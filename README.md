# 小满 · 餐饮 AI 智能经营助手 — 客户解决方案（Slidev）

一份面向餐饮客户的商业解决方案演示，共 **10 页**。

核心表达：

> **让现有系统负责记录，让 AI 负责理解，让老板负责决策。**

## 快速开始

```bash
npm install
npm run dev       # 本地演示，默认 http://localhost:3030
npm run build     # 构建为可部署的静态站点（dist/）
```

演示直接跑在浏览器里：`npm run dev` 打开 <http://localhost:3030>，<kbd>空格</kbd>/<kbd>→</kbd> 翻页。
交付形态就是这个网页本身，不需要额外导出。若确实要 PDF，在演示页用浏览器「打印 → 另存为 PDF」，
纸张选横向、边距设为无、并勾选背景图形即可（16:9）。

演示时常用快捷键：<kbd>空格</kbd>/<kbd>→</kbd> 下一页、<kbd>o</kbd> 目录概览、<kbd>p</kbd> 演讲者模式（含备注）。

## 关键口径（对外表达时保持一致）

- 小满 **不是 ERP**，不替代收银 / 库存 / 采购，也**不做系统之间的强制中间件**。
- **ERP（联锁云）= 经营数据底座**，负责记录已发生的业务事实：销售、库存、采购、报损、供应商、菜品配方。
  第 2 页对外统一说 **「ERP」**，不点名具体厂商。
- **小满 = AI 智能经营层**，负责读取这些数据 → 理解 → 分析 → 预测 → 给出建议。
- 数据接入采用 **可适配架构**：能通过现有系统拿到的走现有系统，拿不到的由小满直接接入数据源；不假设客户当前已有某种连接。
- **AI 助手和 AI 前台不是两套独立的 AI**。底层是同一套模型 / 工具 / 数据与知识能力；上层权限是 **二维** 的 —— **对话者身份**决定能读到哪些数据，**AI 角色**决定能用哪些工具，两个维度取交集才是一次回答的范围。顾客就算对着 AI 助手说话，也拿不到经营数据。
- **小满采用「统一 AI Core + 多角色 Profile」架构**，不为老板、店长、客户分别建设独立 Agent。
  角色差异全部收敛到 Role Profile 的五个字段：**身份、数据权限、可用工具、知识范围、上下文**。
- **Role Profile 就是安全边界**：**默认拒绝**（没写进 Profile 的数据 / 工具 / 知识一律不可用）、
  **入口绕不开**（换入口不换权限判定，顾客对着 AI 助手说话也拿不到经营数据）、
  **全链路过滤**（数据读取 / 工具调用 / 知识检索三段共用同一套权限）。
- **工具、数据、知识都只建一套**：统一 Tool Registry（工具集中注册，权限决定谁能调用）、
  统一数据服务（一套库 + 数据权限过滤，不为角色建独立数据库）、Knowledge Service（统一检索 SOP /
  菜品资料 / 经营制度 / 服务规则，检索结果同样过权限）。**角色可以不断增加，底层系统不需要跟着复制扩张。**
- **AI 调度器是轻量的**：只做身份识别、会话管理与任务路由，不承担复杂推理；
  推理、上下文、记忆、Tool Calling 都在 AI Core 里。
- 整体原则：**统一 AI Core + 多角色 Profile + 统一工具池 + 权限系统 + 统一数据服务 + Knowledge Service + 轻量调度器**。
- **页面上说人话，术语留在文档里**：幻灯片一律用业务语言，上面这套技术名词不出现在页面上。
  对照关系 —— AI Core→**统一 AI 底座**、多角色 Profile→**多角色配置**、Tool Registry→**工具清单**、
  Role Profile 权限→**角色权限**、Knowledge Service→**知识库**、Agent 层→**AI 层**、交互端→**界面端**、
  数据与知识支撑层→**数据与知识底座**、RAG / 向量检索→**按意思找资料**、Tools Calling→**工具调用**、
  五层解耦→**五层各管一件事**。讲稿（演讲者备注）里保留原术语，方便自己讲。
- 补货闭环始终保留 **老板确认** 这一步 —— **AI 负责建议，老板负责最终决策**。
- **补货建议要落到现实约束上**，不能只报一个数字。建议里必须带：**供应商**（找谁买、报价、账期、供货稳不稳）、
  **供货方式**（配送日、起订量、到货时效）、**在途库存**（已下单未到货的不重复买）、**库容与保质期**。
  客户最关心的是"这条建议明天能不能真的执行"。
- **可行性不取决于客户"先具备什么"**：不自研模型、不要求数据一次接全、不改造现有系统。
  风险（数据不全 / 系统封闭 / AI 偏差 / 数据安全）**只在客户问到或答疑环节口头讲**，页面上不再单独成页 ——
  每条都要主动给兜底设计，不要等客户追问。
- **技术栈**：交互端 **uni-app**（一次开发多端运行，小程序 / H5 / App 一套代码）、
  服务端 **Node.js**（统一数据服务 / 工具服务 / 权限系统 / 数据接入，与前端同一套语言）、
  Agent 层 **Agent Harness 基于 pi 二次开发**（跑在服务端内的 AI 骨架，承载推理循环、上下文、
  记忆与 Tool Calling；小满只在其上做业务定制：Tool Registry、Role Profile 权限、Knowledge Service）。
  **模型可替换、数据源可插拔**，选型不绑死任何一家。
- **报价**：MVP 一次性交付 **¥8 万**，交付周期两个月。
  页面上列出计价依据 —— 中国软件行业协会《软件开发和服务项目价格构成及评估方法》：
  **软件开发价格 = 开发工作量 × 开发费用/人月**，**开发工作量 = 估算工作量经验值 × 风险系数 σ × 复用系数 τ**
  （σ = 1.5，τ = 0.9）。代入 45 人天 ÷ 21.75 ≈ 2.07 人月 → 2.07 × 1.5 × 0.9 ≈ 2.79 人月，
  开发费用/人月 = 20,000 × 1.45 ≈ 29,000 元 → 2.79 × 29,000 ≈ **8.0 万元**。
  口径是"只做补货这一个闭环"，范围一加人天就要重算。
